Particle MCMC with a noisy likelihood

PMMH takes Metropolis-Hastings and replaces the likelihood with a particle filter's estimate. The chain still targets the exact posterior, at any particle count. What it pays instead is a sticky chain, and the two facts have the same cause.

One line of Metropolis-Hastings changes

And one implementation detail, which is where the whole behaviour comes from

The particle filter takes a parameter value and returns a number: propagate particles, weight them against each observation, resample, and multiply the mean weights. Call that number L̂(θ). Run the filter twice at the same θ and the two numbers differ.

Metropolis-Hastings with an exact likelihood accepts a proposal θ* with probability

r = min (1, p(y | θ*) p(θ*) q(θ | θ*)p(y | θ) p(θ) q(θ* | θ))

PMMH puts the filter's estimate in both places:

r̂ = min (1, L̂(θ*) p(θ*) q(θ | θ*)L̂(θ) p(θ) q(θ* | θ))

Everything else in the algorithm is unchanged. The detail that matters is which of those two hats is recomputed.

## initialise: one filter run, and keep the number θ ← θ₀ ; ℓ ← log L̂(θ₀, u₀) ## each iteration: one filter run, at the proposal only θ* ~ q(· | θ) ℓ* ← log L̂(θ*, u*) log r̂ = [ log p(θ*) + ℓ* ] − [ log p(θ) + ℓ ] + log q(θ | θ*) − log q(θ* | θ) accept, with probability min(1, r̂): θ ← θ* , ℓ ← ℓ* reject: θ and ℓ both unchanged

The stored number ℓ is part of the state of the chain, alongside θ. On a rejection it is carried forward untouched, so the same estimate sits in the denominator of the next acceptance ratio, and the one after that. A run of 300 rejections compares 300 honest proposals against one number that was drawn once.

This is a single filter run per iteration rather than two, which is also the cheaper option. Recomputing the current state's estimate is a real bug with a specific consequence, and the third figure shows what it does.

Why the chain is still exact

The pseudo-marginal argument, on the enlarged space where the algorithm actually lives

Plugging a random number into an algorithm derived for a fixed one should break it. It does not, and the reason is not that the noise averages out over the run. It is that PMMH is an ordinary Metropolis-Hastings chain, on a space one step larger than the one you were looking at.

The extended target

Write u for every random number the filter draws in one run: the initial particles, the transitions, the resampling indices. It is drawn from a density m(u) that does not depend on θ. The estimate is a deterministic function of the pair, L̂(θ, u), and it is non-negative. The one property required of it is unbiasedness, which the bootstrap filter has for every particle count J and every θ (Del Moral 2004, Proposition 7.4.1):

∫ L̂(θ, u) m(u) du = p(y | θ)   ## for every θ, and every J ≥ 1

Now define a distribution over the pair (θ, u), by treating the estimate as though it were the likelihood:

π̃(θ, u) = p(θ) L̂(θ, u) m(u)p(y)

Integrating u out of it uses the unbiasedness line above and nothing else:

∫ π̃(θ, u) du = p(θ) p(y | θ)p(y) = π(θ | y)   ## the posterior you wanted

So π̃ is a genuine distribution whose θ-margin is the posterior. The last step is to check that PMMH is Metropolis-Hastings for it. Propose the pair from q(θ* | θ) m(u*), meaning propose θ* as usual and draw fresh filter randomness. The Metropolis-Hastings ratio for π̃ under that proposal is

r̃ = p(θ*) L̂(θ*, u*) m(u*) · q(θ | θ*) m(u)p(θ) L̂(θ, u) m(u) · q(θ* | θ) m(u*) = p(θ*) L̂(θ*, u*) q(θ | θ*)p(θ) L̂(θ, u) q(θ* | θ)

The m terms cancel because the filter's randomness is proposed from exactly the density it carries in the target. What is left is the ratio the code computes, which never mentions u at all. PMMH is therefore standard Metropolis-Hastings on (θ, u), it satisfies detailed balance for π̃, and its θ-margin is the posterior. Andrieu & Roberts (2009) set this out as the pseudo-marginal method, and Andrieu, Doucet & Holenstein (2010) established it for particle filters.

Two things follow immediately. The chain is exact at any particle count, including J = 1, where the filter is a single simulated trajectory. Particle count buys efficiency and nothing else. And the stored estimate is not an approximation being carried around. It is the u-half of the current state, and dropping it would mean leaving the state space the argument is built on.

The cost is written into the target

The extended target does not treat filter randomness evenly. It weights u by L̂(θ, u), so draws that happened to return a high estimate get more mass. Take the standard idealisation of the filter's error, a log-normal estimate with the mean correction that makes it unbiased,

log L̂(θ, z) = log p(y | θ) + σ z − σ²/2 ,   z ~ N(0, 1)

Under π̃ the auxiliary variable is distributed as N(σ, 1) rather than N(0, 1). The chain sits, on average, at estimates that are σ²/2 log-units above the truth. That is the tilt the figure below draws, and it is the same tilt that makes the chain stick. Paying for exactness and getting stuck are one event described twice.

Now move b, which tilts the estimate by a factor eb(θ−0.8) and so breaks unbiasedness in a way that depends on θ. The θ-margin slides off the posterior by b × 0.2, the bias times the posterior variance. Unbiasedness is the whole requirement, and it is a requirement on the estimate of the likelihood, not of the log-likelihood.

A constant multiplicative bias would cancel between numerator and denominator and change nothing. A bias that varies with θ moves the answer. This is why averaging several filter runs must be done on the estimates rather than on their logarithms: the mean of the logarithms is not the logarithm of the mean, and the gap between them depends on how noisy the filter is at that θ.

The mechanism. A proposal is accepted partly on its merit and partly on the luck of its filter run. Once a lucky run is accepted, its estimate becomes the number every later proposal has to beat, and a proposal has to be lucky in turn to displace it. The excess panel makes this visible: each plateau in the trace sits under a raised step in the excess. The average height of those steps approaches σ²/2, which is what the extended target predicts, so a filter twice as noisy leaves the chain defending a value four times further above the truth. That average needs accepted moves to average over, so at the noisy end of the slider it has not settled and the measured mean sits below the line.

Sweep σ upwards and the acceptance rate falls, the plateaus lengthen, and the pooled histogram stays on the exact posterior. At σ = 5 it turns ragged and the pooled SD reads nearer 0.40 than 0.447. Eight chains that accept one proposal in a hundred hold very few independent draws between them, so that gap is Monte Carlo error. Longer chains scatter either side of 0.447 rather than settling below it. The excess panel thins out at the same settings. Acceptance is 4.3% at σ = 3 and 0.9% at σ = 5, and the mean excess reads 3.7 and 4.6 against a line drawn at 4.5 and 12.5. Running a hundred times longer brings those to 4.3 and 8.9, so the gap is the running mean failing to settle rather than the prediction failing.

Now press "recomputed every iteration". This is the version that evaluates the filter at the current θ as well as at the proposal, which looks like the obvious way to avoid holding a stale number. The plateaus disappear and the posterior inflates: at σ = 1 the pooled SD goes from 0.447 to about 0.54, at σ = 3 to about 0.77. Redrawing u at every step is an update of the u-half of the state that no accept-reject step accounts for, so the chain no longer preserves π̃. The proposal is offered a fresh chance to be lucky at every iteration and the current state is never allowed to hold on to one, so the chain wanders outward. Stickiness is not a flaw sitting next to the correctness argument. It is what the correctness argument costs.

How many particles

Linear cost against a variance that decides how far the chain moves

Each iteration runs the filter once, so the cost per iteration is proportional to the particle count J. The variance of the log-likelihood estimate falls roughly as 1/J, so its SD falls roughly as 1/√J. More particles buy movement per iteration and charge for it linearly. Somewhere in between sits a minimum.

The curve below is computed by running the toy chain at each particle count. They are not settings to copy. Why not NUTS

Two obstacles, and the second is the one that cannot be worked around

The first is that the likelihood is not differentiable. Resampling picks ancestor indices, the Gillespie simulator fires discrete events, and neither is a smooth function of the parameters. There is no gradient to hand to a gradient-based sampler.

The second is that the filter returns a different number every run. Hamiltonian methods integrate a trajectory along a fixed surface, using the gradient of the log-posterior at each step of the integrator. Here there is no fixed surface. Evaluate at the same θ twice and you are on two different surfaces, so the trajectory is not following anything.

The figure evaluates the estimated log-likelihood on a grid, three independent times, and takes a central finite difference at the marked point. The slider for the step size h shows the bind: the noise in the slope estimate is σ/(h√2), so shrinking h to control the discretisation error multiplies the noise.

What Metropolis-Hastings uses and Hamiltonian methods cannot. The accept-reject step needs the estimate to be right on average, and the pseudo-marginal argument turns that into exactness. A gradient has no such rescue. The filter has no unbiased estimate of the log-likelihood to differentiate, and u is redrawn at every evaluation, so an integrator never sees the same surface twice. This is why the practical reaches for robust adaptive Metropolis (Vihola 2012), which learns the proposal covariance during warmup without ever asking for a derivative.

The figure shows the second obstacle only. Non-differentiability is not visible here, because the toy target has a smooth exact likelihood and the noise is added to it. In a real filter the two arrive together.

Common questions

The ones that come up in the practical, and one that comes up as a bug

Does the filter's noise bias my posterior?

No. As long as the filter's estimate of the likelihood is unbiased, the chain targets the exact posterior at any particle count. The noise costs efficiency, which shows up as a low acceptance rate and long plateaus, and a chain that has not run long enough will look wrong for that reason rather than from bias.

Why does my chain sit still for 300 iterations?

Because the estimate stored at the current state was a lucky draw, and it stays in the denominator until something beats it. Under the target, the stored estimate sits σ²/2 log-units above the truth on average, so plateaus lengthen quickly as the filter gets noisier. Adding particles is the fix, not adding iterations.

Should I use more particles or more iterations?

Within the target band the total cost is flat, so once the filter is calibrated the rest of the budget goes on iterations. The particle filters page covers how to measure the SD and what to aim at.

Can I recompute the likelihood estimate at the current state as well?

No, and it is a common bug because it looks like an improvement. The current state's u is part of the state, and redrawing it with no accept-reject step leaves the chain no longer invariant for the extended target. The plateaus vanish and the posterior comes out too wide, which is easy to miss because the trace looks better.

Can I fix the random seed so the filter is reproducible?

Fixing the seed inside the likelihood makes L̂ a deterministic function of θ, so the chain becomes ordinary Metropolis-Hastings for that fixed function. It is exact for the wrong target: one perturbed realisation of the posterior, with the size of the perturbation set by the filter's variance. Seed the run as a whole for reproducibility, and let each filter call draw fresh randomness.

Why robust adaptive Metropolis rather than plain Metropolis-Hastings?

With six correlated parameters, a proposal that ignores the correlation aims most of its moves in directions the posterior does not extend, and hand-tuning six variances to fix that takes several pilot runs. RAM learns the proposal covariance during warmup and scales it towards a target acceptance rate. Adaptation stops at the end of warmup, so the chain that is kept is an ordinary Metropolis chain with a well-chosen proposal.

What is particle Gibbs, and when would I want it?

Particle Gibbs runs a conditional filter that keeps one reference trajectory from the previous iteration, then updates the parameters given that trajectory. It suits models where the parameters have conditional structure worth exploiting given the path, and it avoids PMMH's stickiness because the path is updated rather than accepted or rejected wholesale. Its own failure mode is path degeneracy, which leaves the early states of the reference trajectory barely changing, and ancestor sampling is the standard repair (Lindsten et al. 2014).

Does any of this depend on it being a bootstrap filter?

No. The argument needs a non-negative, unbiased estimate of the likelihood, and auxiliary and guided filters supply one as long as the weights are correct. Better filters reduce the variance, which moves you along the cost curve, and leave the exactness argument untouched.
